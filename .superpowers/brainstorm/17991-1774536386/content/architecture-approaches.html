MC Skills Integration — Architecture Approaches

How should Claude Deck orchestrate the MC engineering workflow?

A

Skill Proxy — Deck invokes skills via Claude Code CLI

Claude Deck spawns claude --resume <session> -p "/start-work VEC-24" in the target repo. Each stage transition = one CLI invocation with the skill as the prompt. Deck parses the structured output (plan.md, review findings, PR URLs) and renders it in the UI.

Pros

  • Uses MC skills exactly as designed — no forking or reimplementing
  • Skills auto-update when configure-claude runs
  • Session resume preserves full conversation context
  • CLAUDE_HIVE=1 enables non-interactive mode (no user prompts)
  • Skills handle Linear status transitions, branch creation, etc.

Cons

  • Must parse skill output (plan.md) to render structured UI
  • 60s+ MCP init per invocation (same as current planning agents)
  • Skills may prompt for input — need to handle or suppress
B

Skill-Inspired — Deck reimplements the workflow with its own agents

Claude Deck reads the SKILL.md files as reference but builds its own orchestration. Uses MCP tools directly (same as current planning agents) but follows the MC workflow stages. Doesn't invoke /start-work etc. — implements equivalent behavior.

Pros

  • Full control over agent behavior and output format
  • Can enforce structured JSON output instead of parsing markdown
  • No dependency on skills being installed locally

Cons

  • Duplicates and diverges from the team's shared workflow
  • Must reimplement: code discovery, plan format, review agents, Linear transitions
  • Maintenance burden — skills evolve, reimplementation falls behind
  • Loses the "code detective", "devdocs reviewer", and other shared agents

💡 Recommendation: Option A

Use the real MC skills via CLI. The skills already handle 90% of the workflow — code discovery, plan format, parallel agents, verification, Linear transitions, PR creation. Deck's job is orchestration + UI, not reimplementation. Parse the structured output (.work/plan.md, review files) into rich UI components.

The 60s MCP init cost is already acceptable (current planning agents have the same cost). CLAUDE_HIVE=1 handles the non-interactive requirement.
