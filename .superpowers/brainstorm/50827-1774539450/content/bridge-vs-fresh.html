Skill Execution — Bridge vs Fresh Process

Both use stream-json for MCP access. The question is process lifecycle.

A

Persistent Bridge Per Repo

One long-lived Claude Code process per active repo. Skill invocations are messages sent to the same process. Context accumulates naturally.

Pros

  • ~200-400MB RAM per repo (not per skill call)
  • MCP init only once — subsequent skills start instantly
  • Conversation context accumulates (no --resume overhead)
  • Already proven pattern (poll bridge works reliably)

Cons

  • Crash = lose conversation (must re-init from .work/ files)
  • One process per repo — can't run two skills in parallel on same repo
  • Long-lived process may accumulate stale context
B

Fresh Process + Session Resume

New Claude Code process per skill invocation. Uses --resume <session-id> to restore conversation context from disk. Process dies after skill completes.

Pros

  • Crash-resilient — session on disk, just resume
  • Clean process state each time
  • Can run multiple skills in parallel (different tasks)

Cons

  • 60s MCP init EVERY invocation (~400MB each)
  • More total RAM when multiple tasks active
  • --resume still loads full session — overhead unclear
C

Hybrid — Bridge While Active, Kill When Idle

Spawn a bridge when user clicks "Start Work". Keep it alive through /hack, /ship, /code-review. Kill it when the task moves to "done" or after 30min idle.

Pros

  • Fast skill transitions during active work (no re-init)
  • RAM freed when task is done or user walks away
  • Natural lifecycle — bridge lives as long as the task is active
  • Crash recovery: restart bridge, context in .work/ files

Cons

  • Slightly more complex lifecycle management
  • Need to track which bridge belongs to which task/repo

💡 Recommendation: Option C (Hybrid)

Best of both worlds. During active work on a task, the bridge stays alive — skill transitions are instant (no 60s MCP init between /start-work and /hack). When the task is done or idle, the bridge dies and RAM is freed. The .work/ directory on disk is the durable state; the bridge is just the execution context.

This maps naturally to the user's workflow: click "Start Work" → bridge spawns → work through stages → task completes → bridge dies.
